Two blockers remain:

1. **Preserve existing unexpired pins across startup and snapshot adoption.**  
   Rewriting the consumer file from an older HA backup can erase pins protecting playback that continues through HA restart. Require startup/adoption to merge existing on-disk unexpired pins with restored pins, never shorten their expiry, and serialize all writes for that consumer under the integration’s lock. Snapshot changes must preserve pins for renders removed from the snapshot. Shared `flock` excludes GC but does not serialize competing integration writers. ([Consumer-file/adoption rules](/Users/jdavidoa91/Dev/hass-cinema-studio/docs/superpowers/specs/2026-10-05-cinema-studio-design.md:171))

2. **Keep imported renders unpublished until the final manifest check succeeds.**  
   The current import publishes validated links, then proposes quarantining them if the post-import manifest changed. A catalog refresh could already expose those renders to selection; moving them would invalidate protected URIs.

   Require a staged import: link/hash/probe privately, re-fetch and reconcile the manifest, then publish accepted clips. If any render has already been published, withdraw it through normal retirement/GC rather than quarantine. Apply byte-identity checks to imported originals too, since they become the source for future renders. ([Import sequence](/Users/jdavidoa91/Dev/hass-cinema-studio/docs/superpowers/specs/2026-10-05-cinema-studio-design.md:401))

The filesystem fence otherwise resolves the GC race, and the revised orphan handling and compiled-output fingerprint check are acceptable.
